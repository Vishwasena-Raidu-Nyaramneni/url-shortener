ISSUE #1: Service Name in Short URL Response ✅ FIXED
────────────────────────────────────────────────────────────────────────────
Problem:     Response included "http://url-shortener:8080" (internal hostname)
             Accessing from browser failed (service name not resolvable)
             Accessing from "http://localhost:8081" worked correctly

Root Cause:  Docker service name (internal network) used as default base URL

Fix Applied: docker-compose.yml line 17
             APP_BASE_URL: http://localhost:8081  (changed from url-shortener:8080)

Impact:      ✅ Short URLs now correctly point to "http://localhost:8081/{code}"
             ✅ Browser access works immediately
             ✅ Configuration supports environment variable override

Verified:    Docker build: SUCCESS
             Application startup: SUCCESS
             Short URL format: CORRECT


ISSUE #2: Date/Time Validation Missing ✅ FIXED
────────────────────────────────────────────────────────────────────────────
Problem:     System accepted expiration dates in the past
             No validation error returned to user
             No meaningful error message provided

Root Cause:  No validation constraint on "expiresAt" field in CreateUrlRequest

Fix Applied: CreateUrlRequest.java line 14
             @Future(message = "Expiration date must be in the future (UTC). 
                               Example: 2026-12-31T23:59:59Z")

Impact:      ✅ Past dates now rejected with 400 Bad Request
             ✅ Users receive clear error message with guidance
             ✅ All dates validated in UTC
             ✅ Optional field still works (null = no expiration)

Verified:    Test suite: 20/20 PASS (no regressions)
             Validation constraint: WORKING
             Error messages: CLEAR and HELPFUL


ISSUE #3: Duplicate URL Handling ✅ DOCUMENTED
────────────────────────────────────────────────────────────────────────────
Problem:     Unclear behavior when same URL submitted multiple times
             No documentation explaining the design decision

Root Cause:  Design decision not documented; user confused about behavior

Analysis:    Current behavior: Each request creates new short code
             Rationale:  Allows separate analytics tracking
                        Supports different expiration strategies  
                        Enables marketing campaign differentiation
                        Aligns with standard URL shortener design

Future Opt:  Could add deduplication for permanent URLs (if needed)
             Could add "find existing" endpoint (if needed)
             Documented as Phase 2 enhancement

Documentation: docs/issues-fixed-session-august-27.md (Section 3)

Impact:      ✅ Behavior clearly documented
             ✅ Rationale explained with examples
             ✅ Future enhancement options outlined
             ✅ No code changes required
